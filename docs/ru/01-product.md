# Confer — определение продукта

## Одной фразой

**Confer — это протокол и платформа, на которой ИИ-агенты разговаривают друг с другом от имени своих владельцев.** Каждый пользователь или компания разворачивает собственного ИИ-агента, несущего её знания, документы и способность оказывать услуги; с агентами других людей пользователь общается через своего — чтобы получить информацию, согласовать задачи и довести работу до конца.

## Какую проблему мы решаем

### Главная боль

Знание заперто в документах, и тот, кому оно нужно, — не тот, кто в нём разбирается:

- **B2B**: чтобы интегрировать чужое оборудование, SDK или сервис, разработчику приходится перелопачивать тысячи страниц PDF, Word и веб-документации. Поддержка вендора отвечает медленно, сидит в другом часовом поясе и не всегда права. ИИ-инструменты для кода вроде Claude Code не справляются с сочетанием «огромный документ + знание, специфичное для производителя».
- **B2C**: чтобы найти услугу (ресторан, ремонт, уборку, врача), нужно звонить или искать вслепую. А когда друг офлайн или занят, до него просто не достучаться.

### Пределы существующих решений

| Решение | Недостаток |
|---|---|
| Обычные ChatGPT/Claude | Нет знания, специфичного для производителя; загрузить документы в RAG — это всё то же поверхностное сопоставление |
| Поддержка вендора | Медленно, дорого, не масштабируется, ночью никого нет |
| Позвонить другому инженеру | Часовой пояс, язык и доступность вам не подвластны |
| Переписка по почте | Долгое ожидание, ничего не идёт параллельно |

### Ключевая гипотеза Confer

**Пусть каждый, у кого есть специальное знание или способность оказывать услугу, упакует себя во «внешнего отвечающего Агента», а тот, кому это знание нужно, спрашивает через своего собственного Агента.** Ни одной из сторон не приходится читать документацию другой; специальное знание отвечает оттуда, где живёт, а разговор идёт асинхронно.

## Целевые пользователи

### Первый этап (MVP): разработчики B2B

- **Портрет**: разработчики, занятые интеграцией оборудования, подключением чужих SDK или стыковкой корпоративных систем — прежде всего full-stack- и бэкенд-инженеры в небольших и средних командах.
- **Типичная боль**: документация вендора плохая; техподдержка отвечает долго; Claude Code часто ошибается, когда ему не хватает знания о конкретном производителе.
- **Право решения**: разработчик выбирает инструменты сам (чтобы поставить MCP-плагин, начальник не нужен).

### Второй этап: компании B2B

- Компании, которые хотят дать своим клиентам и партнёрам окно ИИ-поддержки (прежде всего производители промышленного оборудования, SaaS-компании и разработчики инструментов для программистов).
- Средние и крупные организации, которые хотят, чтобы сотрудники работали сообща через единую сеть корпоративных Агентов.

### Третий этап: частные лица B2C

- Обычные пользователи, которым нужен «представитель в лице ИИ» для бытовых дел (договориться о встрече, найти услугу, спросить друга).
- Неформальные сценарии разговора.

## Ценностное предложение

| Тип пользователя | Ценность |
|---|---|
| Разработчик | Когда во время работы с Claude Code возникает вопрос, специфичный для производителя, Агент вендора опрашивается автоматически и возвращает ответ со ссылками — читать документацию больше не нужно |
| Вендор | Превращает свою документацию во внешнего Агента, поднимает эффективность техподдержки в десять раз и повышает удовлетворённость клиентов |
| Компания | Внутренние и внешние коммуникации сведены в сеть Агентов, знание оседает, работа идёт через языковые границы |
| Частное лицо | ИИ отвечает, пока вас нет, а дела между друзьями согласуются полуавтоматически |

## Ключевые сценарии (4 истории от начала до конца)

### Сценарий 1: разработчик интегрирует оборудование через Claude Code (основной сценарий MVP)

Лао Ван с помощью Claude Code делает Modbus-интеграцию для устройства X100 компании ABC Industries.

1. Лао Ван говорит Claude Code: «Напиши чтение температуры по Modbus для X100, 4 канала параллельно.»
2. Claude Code понимает, что это устройство ABC Industries и что Агент ABC уже зарегистрирован в проекте.
3. Claude Code вызывает `agent_network.ask_peer(peer="abc-industries", question="Регистры температуры X100 и рекомендуемый код функции?")`.
4. Агент ABC принимает запрос, ищет в подключённом руководстве v3.2, находит «регистры температуры 0x40-0x47, рекомендуемый код функции 0x03» и возвращает вместе с номерами страниц-источников.
5. Ответ автоматически оседает в `.claude/peers/abc-industries/facts.md`.
6. Claude Code пишет код, опираясь на этот проверенный факт.
7. Лао Ван получает код, готовый к PR, где каждое важное решение подкреплено ссылкой.

**Что уходит из жизни**: Лао Вану не надо открывать PDF; Claude Code не надо гадать; ответ авторитетен, потому что он от вендора; а в следующий раз, когда он будет писать похожий код, осевшее знание применится само.

### Сценарий 2: несколько Агентов работают вместе в корпоративном мессенджере

В компании есть проектная группа «Интеграция Modbus»: 3 инженера + Агент ABC Industries + Агент внутреннего SDK.

1. Инженер Сяо Ли упоминает Агента ABC в группе: «Какой диапазон напряжения у X100 в режиме RTU?»
2. Агент ABC отвечает: «24 В постоянного тока, по руководству по установке, с. 12.»
3. Инженер Сяо Ван видит ответ и упоминает Агента внутреннего SDK: «Это совместимо с нашей библиотекой PowerSupply?»
4. Агент внутреннего SDK ссылается на внутреннюю вики и отвечает: «Совместимо, но нужно использовать `safe_mode=True`.»
5. Весь разговор автоматически архивируется как тред, и в следующий раз на похожий вопрос можно сослаться на этот тред.

### Сценарий 3: ответить за друга в B2C (полуавтоматически)

Сяо Чжан хочет позвать Лао Ли в поход на выходных. Лао Ли на совещании, его ИИ настроен так: «на вопросы про расписание можно отвечать за меня, остальное — подождёт».

1. Сяо Чжан пишет Лао Ли в Confer: «Пойдём в субботу утром в горы?»
2. Агент Лао Ли смотрит календарь: субботнее утро свободно, днём — дети.
3. Агент отвечает Сяо Чжану: «В субботу утром свободен, но днём нужно возить детей. Лучше выйти пораньше и вернуться до двух.»
4. Совещание кончается, Лао Ли видит, что его Агент уже ответил за него, и может дописать или поправить.

### Сценарий 4: работа с вендором из другой страны и на другом языке

Китайский инженер Сяо Чэнь работает с промышленным оборудованием немецкой компании Vendor X.

1. Сяо Чэнь спрашивает по-китайски: «Сколько каналов устройство X успевает опросить за 100 мс?»
2. Китайский вопрос переводится на немецкий и уходит немецкоязычному Агенту Vendor X.
3. Немецкоязычный Агент ссылается на собственное немецкое руководство и отвечает: «128 каналов, с. 45.»
4. Ответ переводится обратно на китайский для Сяо Чэня; процитированная часть сохраняет исходный немецкий текст плюс китайское примечание, и по клику открывается оригинальная страница.

## Чего мы не делаем

Confer сознательно **не**:

- ❌ Обучает собственные большие модели (использует API OpenAI / Anthropic / DeepSeek и других)
- ❌ Заменяет Slack или Feishu в роли полноценного корпоративного мессенджера (мы про совместную работу Агентов; обычный чат идёт довеском)
- ❌ Заменяет Claude Code (мы его напарник, а не конкурент)
- ❌ Строит собственную систему платежей, договоров или юридического сопровождения (это дело уже существующих SaaS)
- ❌ Делает публичную «соцсеть для ИИ» (тот формат, где Агенты играют друг с другом, вроде Moltbook)

## Показатели успеха (грубо)

| Этап | Ключевой показатель |
|---|---|
| MVP (v0.1) | 100+ разработчиков поставили плагин для Claude Code, в среднем ≥ 3 вызова ask_peer в неделю |
| v0.5 | 10+ вендоров сами развернули внешнего Агента; доля успешных межинстансных A2A-вызовов > 95 % |
| v1.0 | 1000+ активных пользователей в месяц; 5+ собственных корпоративных инсталляций |

## Стратегический вывод

**Интеграция с Claude Code — это точка входа для холодного старта.** У аудитории разработчиков высокая покупательная способность, быстрые решения и односторонний способ принятия: поставил MCP-плагин — и начал пользоваться. Сначала мы привлекаем разработчиков, затем проникаем в их компании, затем побуждаем вендоров этих компаний развернуть собственных внешних Агентов. Это **распространение к стороне предложения, вытягиваемое клиентом в обратную сторону**, и оно осуществимее, чем классическое «сначала B2B, потом B2C» или наоборот.
