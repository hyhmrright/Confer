# Confer — Спецификация API

Определяет все API между клиентом и сервером, а также между сервером и пирами A2A.

## Общие соглашения

- Base URL: `https://{instance}/api`
- Кодировка: JSON, UTF-8
- Формат времени: ISO 8601, UTC (`2024-11-15T14:30:00Z`)
- Идентификаторы: ULID (`01HXKQ7Z2N3M4P5R6T7Y8Z9A0B`)
- Формат ошибки:

```json
{
  "error": {
    "code": "invalid_request",
    "message": "Human-readable message",
    "details": { /* optional */ }
  }
}
```

## Аутентификация

- Клиент пользователя: `Authorization: Bearer <jwt_access_token>`
- TTL access-токена — 15 минут, TTL refresh-токена — 90 дней
- Два токена различаются утверждением `typ` (`access` / `refresh`) и **не взаимозаменяемы**: заголовок `Authorization` принимает только `access`, а `POST /auth/refresh` — только `refresh`. Раньше они отличались лишь полем `exp`, из-за чего refresh-токен работал как 90-дневный пропуск на любом защищённом эндпоинте, а 15 минут access-токена не значили ничего
- Refresh обновляется при каждом использовании и сверяется с `sessions.refresh_token_hash`; несовпадение считается повторным использованием, и вся сессия аннулируется. `sessions.expires_at` — **абсолютный** предел сессии: ротация его не продлевает
- Токены хранятся в локальном хранилище клиента, а не в HTTP-only cookie (клиент — настольное приложение на Tauri, где у cookie того же origin просто нет аналога)

### Настройки пользователя и Агента

```
GET    /api/v1/users/me
PATCH  /api/v1/users/me
GET    /api/v1/agents/me
PATCH  /api/v1/agents/me
PUT    /api/v1/agents/me/policies
GET    /api/v1/agents/me/llm-keys      # настроен ли каждый поставщик (возвращает только булевы значения, никогда сам ключ)
PUT    /api/v1/agents/me/llm-keys      # сохраняет ключи API для LLM в зашифрованном виде
DELETE /api/v1/agents/me/llm-keys/{provider}
GET    /api/v1/agents/me/llm-keys/{provider}/models   # запрашивает у поставщика в реальном времени список его моделей
```

Значения `provider` берутся из каталога поставщиков в `@confer/shared` (`packages/shared/src/llm/catalog.ts`) плюс инструментальный сервис `tavily`. Каталог читают сразу шлюз, agent-runtime и клиент: базовый URL, путь к списку моделей и модель по умолчанию записаны ровно в одном месте, поэтому добавление поставщика затрагивает только каталог.

`/models` пересылает список моделей самого поставщика и никогда не возвращает список, который ведётся у нас:

```jsonc
{ "models": [{ "id": "gpt-4o" }] }
// пустой список всегда несёт причину; все четыре различны и требуют разных действий
{ "models": [], "error": "no_key" }        // для этого поставщика ещё не настроен ключ
{ "models": [], "error": "unauthorized" }  // поставщик отклонил ключ (401/403)
{ "models": [], "error": "unreachable" }   // до поставщика не достучаться или он вернул иную ошибку
{ "models": [], "error": "unsupported" }   // этот поставщик не даёт эндпоинта со списком моделей
```

### Контакты / чужие Агенты

```
GET    /api/v1/contacts                     # перечисляет контакты. Постраничность: ?limit=&offset=
POST   /api/v1/contacts                     # добавляет контакт
GET    /api/v1/contacts/{contact_id}        # подробности контакта (вместе с пиром)
DELETE /api/v1/contacts/{contact_id}
PATCH  /api/v1/contacts/{contact_id}        # частично меняет alias / tags / pinned / muted (непереданные поля не очищаются)

POST   /api/v1/contacts/lookup              # поиск по DID / домену / имени пользователя
```

`POST /api/v1/contacts/lookup` запрос:

```json
{
  "method": "domain",          // domain | did | username | qr_code | phone
  "value": "abc-industries.com"
}
```

`GET /api/v1/contacts` возвращает `{ contacts, total }`. `limit` по умолчанию 50 и не больше 100, `offset` по умолчанию 0; сортировка идёт по `id` (ULID) по убыванию, то есть самое свежее первым — именно единственный и детерминированный порядок не даёт окну offset пропускать или повторять строки. `total` — это полный счёт, а не число записей на странице, и по нему клиент понимает, что дошёл до конца. Нечитаемые `limit` и `offset` берут значения по умолчанию, а не приводят к ошибке.

Ответ: список найденных Агентов-кандидатов. Поиск **записывает найденных пиров в `peer_agents`** и добавляет к каждому кандидату локальный `id` (`peer_id`) — именно этот `id` и использует `POST /api/v1/contacts` для добавления контакта. `POST /contacts` идемпотентен: повторное добавление того же пира возвращает уже существующий контакт (`200`), а не ошибку.

> Добавление контакта — это **согласие принимающей стороны на то, чтобы другой расходовал её Агента**: заставить моего Агента отвечать (и тратить мой бюджет на LLM) может только пир, добавленный в контакты. Сообщения A2A от неподключённого пира откладываются как запрос на соединение, ожидающий одобрения; см. «Ворота согласия на соединение» в `03-protocol.md`.

```
POST   /api/v1/contacts/{contact_id}/policies   # задаёт постоянные политики (полная замена, семантика PUT)
```

Тело `POST /contacts/{id}/policies` имеет исполняемую форму `{ default?: 'allow'|'ask_user'|'deny', rules?: [{ action, peer_did?, decision }] }` и целиком записывается в `peer_contacts.policy_overrides_json`. **Семантика слияния**: при решении по входящему запросу A2A это переопределение для контакта накладывается поверх политики Агента — если `contact.default` присутствует, он заменяет умолчание Агента, а `contact.rules` идут перед правилами Агента и потому срабатывают первыми (точное правило для контакта важнее общего правила Агента). Пустое переопределение `{}` — тождество: решение побайтово совпадает с тем, что было бы без него.

### Управление разрешениями

```
GET    /api/v1/permissions/pending               # ожидающие запросы уровней L2/L3
POST   /api/v1/permissions/{id}/decide           # одобрить или отклонить
GET    /api/v1/permissions/history               # история
```

`POST /api/v1/permissions/{id}/decide` запрос:

```json
{
  "decision": "allow_always",       // allow_once | allow_always | deny | deny_always
  "scope": "peer_action"            // область действия решения
}
```

Среди ожидающих запросов те, у которых `action='connect'`, — это **запросы на соединение** (их создаёт входящий путь A2A при первом обращении незнакомого пира). Одобрение (`allow_*`) записывает такого пира в `peer_contacts` и устанавливает связь; отказ — нет.

Те, у которых `action='ask'`, — это **отложенные вопросы от уже подключённого пира**: входящий путь A2A создаёт их, когда политика Агента решает по этому вопросу `ask_user` (см. «Очередь ожидания (ответ в отсутствие хозяина)» в `03-protocol.md`). Одобрение (`allow_*`) заставляет Агента ответить на отложенный вопрос; отказ оставляет его без ответа.

`GET /pending` снабжает каждый запрос полем `description` (у запроса на соединение — кто его начал и первое сообщение; у вопроса — кто спрашивает и текст вопроса), чтобы хозяину было на что опереться.

### Память проекта (для интеграции с Claude Code)

```
GET    /api/v1/projects/{project_id}/peers              # пиры, у которых в этом проекте есть память (name/did подтягиваются join'ом)  ✅ реализовано
POST   /api/v1/projects/{project_id}/peers              # явно регистрирует пира в проекте   🔜 backlog
GET    /api/v1/projects/{project_id}/peers/{peer_id}/facts        # ✅ реализовано
PUT    /api/v1/projects/{project_id}/peers/{peer_id}/facts        # ✅ реализовано
GET    /api/v1/projects/{project_id}/peers/{peer_id}/decisions    # ✅ реализовано
PUT    /api/v1/projects/{project_id}/peers/{peer_id}/decisions    # ✅ реализовано
```

Пояснения к семантике (v0.1):

- Все запросы ограничены `user.sub` (изоляция между пользователями).
- Перед PUT проверяется, что пир является контактом этого пользователя (`peer_contacts`); если нет — возвращается `403 not_a_contact`.
- PUT выполняет upsert: первая запись ставит `version=1`, каждая следующая увеличивает `version` и обновляет `updated_at`. `facts` и `decisions` независимы — запись одного раздела не стирает другой.
- `GET facts/decisions` возвращает `200`, пустую строку и `version:0`, когда у пары (проект, пир) памяти ещё нет (а не 404: «этот пир пока ничего не оставил» — нормальное состояние при чтении).
- `project_id` проверяется выражением `^[a-zA-Z0-9._\-/]+$` (от 1 до 255 символов); при несоответствии возвращается `400 invalid_project_id`.
- `GET peers` на пустом проекте возвращает пустой массив. Связь (проект, пир) возникает неявно при PUT facts/decisions (явной регистрации через `POST peers` на этом этапе нет).

### База знаний (RAG)

```
GET    /api/v1/knowledge-bases                                  # перечисляет мои базы знаний
POST   /api/v1/knowledge-bases                                  # создаёт базу
PATCH  /api/v1/knowledge-bases/{kb_id}                          # меняет имя или описание, а также открыта ли база внешним Агентам
DELETE /api/v1/knowledge-bases/{kb_id}                          # удаляет её вместе со всеми документами и векторами

GET    /api/v1/knowledge-bases/{kb_id}/documents                # постраничность: ?limit=&offset=
POST   /api/v1/knowledge-bases/{kb_id}/documents                # multipart-загрузка, поле называется file
DELETE /api/v1/knowledge-bases/{kb_id}/documents/{doc_id}
POST   /api/v1/knowledge-bases/{kb_id}/documents/{doc_id}/retry # переиндексировать
```

Тело `POST /knowledge-bases` — это `{ name, description? }` (`name` от 1 до 255 символов); ответ — `201` и `{ knowledge_base }`.

Тело `PATCH /knowledge-bases/{kb_id}` — это `{ name?, description?, shared_with_peers? }`; ответ — `{ knowledge_base }`. **`shared_with_peers` меняется только здесь и не принимается при создании**: любая база рождается «только для себя», а открытие её наружу — второе, отдельное и намеренное действие.

`shared_with_peers` решает, **может ли входящий вопрос по A2A искать в этой базе**, и по умолчанию равен `false`. На самого владельца, когда он общается в браузере, это не влияет: он всегда ищет по всему. Эта граница обязана проходить по области поиска, а не по промпту: вопрос чужой стороны и указания владельца доходят до модели как один и тот же вид текста, так что «пусть Агент сам решит, о чём можно говорить» границей не является вовсе. По той же причине входящий вопрос по A2A **не поднимает никакой долговременной памяти**: она выделена из разговоров самого владельца, и ни одна её запись не помечена как пригодная покинуть этот экземпляр.

`GET /knowledge-bases` возвращает `{ knowledge_bases }` и **не разбит на страницы**: базы знаний пользователь заводит руками, и их число ограничено.

`GET /{kb_id}/documents` возвращает `{ documents, total }`. `limit` по умолчанию 50 и не больше 100, `offset` по умолчанию 0; сортировка по `id` (ULID) по убыванию, то есть самое свежее первым — единственный и детерминированный порядок не даёт окну offset пропускать или повторять строки. `total` — полный счёт, а не число записей на странице. Нечитаемые `limit` и `offset` берут значения по умолчанию, а не приводят к ошибке. Это единственный список в этом разделе, растущий без границ, потому что база знаний — как раз то, куда загружают.

Загрузка идёт через `multipart/form-data`, поле файла всегда называется `file`, предел на файл — **10 МБ** (сверх того `400 bad_request`). `Content-Type` берётся из формы, если он там есть, иначе выводится из расширения. Ответ — `201` и `{ document }`, причём `status` уже равен `processing`: **нарезка, векторизация и запись в Qdrant выполняются асинхронно после ответа**, эндпоинт загрузки их не ждёт. Клиент опрашивает список документов, пока `status` не изменится.

Значения `status`:

| Значение | Смысл |
|---|---|
| `processing` | Сохранён, идёт нарезка или векторизация. Начальное состояние после загрузки и после retry |
| `ready` | Доступен для поиска. `chunk_count` — число фрагментов документа |
| `failed` | Индексация не удалась (разбор, отсутствие ключа для embedding или сбой записи в векторную базу) |

`POST /{doc_id}/retry` забирает исходный файл из объектного хранилища и индексирует заново; сначала он стирает уже имеющиеся векторы этого документа, поэтому дублирующихся фрагментов не возникает. Возвращает `400`, если исходного файла больше нет (`storage_key` пуст) или документ всё ещё в `processing`. Ответ — `{ document }`, `status` сброшен в `processing`, `chunk_count` обнулён.

Удаление базы знаний каскадно удаляет все её строки документов и векторы в Qdrant; удаление одного документа вдобавок вычищает его векторы и исходный файл в объектном хранилище. Сбой очистки векторов или объектов не отменяет удаление в базе данных: осиротевший объект лучше строки, указывающей на уже удалённые данные.

Все эндпоинты ограничены `user.sub`: обращение к чужой базе или документу возвращает `404` (а не `403`, чтобы не выдать сам факт существования).

> Обратный прокси должен пропускать тела в 10 МБ. `infra/nginx.conf` задаёт `client_max_body_size 10m` на `/api/`; при стандартном для nginx значении в 1 МБ файлы от 1 до 10 МБ до шлюза попросту не доходят, а браузер получает собственную страницу 413 от nginx.

## WebSocket

### Эндпоинт

```
WSS  /ws?token=<access_token>&device_id=<device_id>
```

Аутентификация при рукопожатии полностью такая же, как в REST, а не «подпись сошлась — проходи»: `typ` обязан быть `access`, `sid` обязан указывать на всё ещё существующую сессию, а учётная запись не должна быть `disabled`. Все три условия необходимы: без них заблокированной учётной записи достаточно непросроченного токена, чтобы переподключаться и продолжать получать сообщения, тогда как сама блокировка (удаление всех сессий) на этом пути ничего не отзывает. Блокировка ещё и **закрывает уже открытые сокеты** этого пользователя: nginx даёт `/ws` `proxy_read_timeout` длиной в сутки, и остановка следующего рукопожатия не останавливает уже установленное соединение.

### Формат сообщений

Все сообщения WS — это JSON с полем `type`:

```json
{ "type": "message.new", "data": { /* ... */ } }
```

### Клиент → сервер

```
ping                          // сердцебиение
subscribe.conversation        // подписаться на разговор (сервер проверяет, что вы его участник)
unsubscribe.conversation
typing.start                  // действует только для разговоров, на которые есть подписка
typing.stop
read.ack                      // подтверждение прочтения
```

Рассылка `typing.*` опирается на набор подписок этого сокета. Когда у подписки ворота есть, а у событий набора текста нет, достаточно знать идентификатор разговора, чтобы вбросить в него «такой-то печатает» — да ещё и под собственным именем пользователя.

### Сервер → клиент

```
pong
message.new                   // новое сообщение
message.updated
message.deleted
typing.update                 // кто печатает
presence.update               // контакт вышел на связь или ушёл
permission.request            // запрос разрешения, по которому должен решить пользователь
agent.status                  // чем занят мой Агент («консультируюсь с Агентом ABC…»)
conversation.updated
```

`message.new` пример:

```json
{
  "type": "message.new",
  "data": {
    "id": "01HXKQ...",
    "conversation_id": "01HX...",
    "sender_type": "peer_agent",
    "sender_id": "01HY...",
    "sender_did": "did:web:acme.com:agents:support",
    "content_type": "text",
    "content": "Кодом 0x03, Read Holding Registers…",
    "citations": [
      {
        "source": "Руководство по связи X100 v3.2",
        "page": 87,
        "url": "https://acme.com/manuals/x100-v3.2.pdf#page=87",
        "trust_level": "authoritative"
      }
    ],
    "language": "ru",
    "created_at": "2024-11-15T14:30:00Z"
  }
}
```

`permission.request` пример:

```json
{
  "type": "permission.request",
  "data": {
    "id": "01HXP...",
    "level": "L2",
    "action": "share_files",
    "scope": {
      "peer": "did:web:acme.com:agents:support",

    "peer_did": "did:web:acme.com:agents:support",

}
```

**В полезной нагрузке нет `description`, и это сделано намеренно.** Сервер не знает, на каком языке читает получатель, поэтому шлёт только структурированные факты (`action` + личность пира + сохранённый `scope`), а фразу, которую видят при одобрении, собирает клиент по своей i18n (`packages/client/src/lib/permission-text.ts`). Этот контракт принадлежит исключительно `permissionRequestEventSchema` из `@confer/shared`: шлюз разбирает им данные перед отправкой, клиент — после получения.

Каждая строка `GET /api/v1/permissions/pending` имеет ту же форму (плюс поле `decision`) и создаётся тем же конструктором, поэтому строка, полученная опросом, и строка, пришедшая через сокет, совпадают побайтово.

## API A2A (наружу, для вызова другими экземплярами Confer)

Подробности — в `docs/03-protocol.md`. Здесь только перечень эндпоинтов.

Две привязки сосуществуют под одним префиксом и проходят одни и те же ворота (`a2a/inbound.ts`); различается лишь формат передачи.

**Стандартная привязка A2A HTTP+JSON** (пути дословно взяты из §11.3 спецификации; именно её объявляет Agent Card):

```
POST   /a2a/v1/message:send              # SendMessage → Task
GET    /a2a/v1/tasks/{id}                # GetTask
GET    /a2a/v1/tasks                     # ListTasks (курсорная постраничность)
POST   /a2a/v1/tasks/{id}:cancel         # CancelTask → TaskNotCancelable
POST   /a2a/v1/message:stream            # не реализовано → UnsupportedOperation
POST   /a2a/v1/tasks/{id}:subscribe      # не реализовано → UnsupportedOperation
GET    /a2a/v1/extendedAgentCard         # не реализовано → UnsupportedOperation
*      /a2a/v1/tasks/{id}/pushNotificationConfigs…  # → PushNotificationNotSupported
```

**Собственный диалект Confer** (между экземплярами; обнаруживается через `/.well-known/agents.json`):

```
POST   /a2a/v1/messages                  # принимает сообщения внешних Агентов
GET    /a2a/v1/stream/{message_id}       # забирает ответ потоком (SSE)
GET    /a2a/v1/agent-facts/{agent_did}   # публичные AgentFacts
```

Все эндпоинты A2A требуют проверки HTTP-подписи сообщения.

## .well-known endpoints

```
GET    /.well-known/did.json                # основной DID-документ
GET    /.well-known/agents.json             # список всех публичных Агентов этого экземпляра

```

## Стандартная Agent Card A2A (слой совместимого обнаружения)

```
GET    /agents/{username}/agent-card.json   # стандартная A2A-карточка этого Агента
GET    /.well-known/agent-card.json         # то же самое, только если у экземпляра ровно один публичный Агент
```

Соответствует `AgentCard` из **Agent2Agent v1.0** Linux Foundation (поля взяты из `specification/a2a.proto` репозитория `a2aproject/A2A` @ v1.0.1, в JSON-отображении proto3, отсюда camelCase). Цель — чтобы экосистема A2A **находила** Агентов этого экземпляра: имена совпадали, а протоколы не сходились, потому что документ обнаружения у той стороны лежит по `/.well-known/agent-card.json`, а у этого экземпляра был только `/.well-known/agents.json`.

Несколько намеренных решений:

- **По одной карточке на Агента**, где `supportedInterfaces[].tenant` — имя пользователя. Well-known в спецификации исходит из «один домен — один Агент», а этот экземпляр многоарендный; `tenant` и есть тот селектор маршрутизации, который спецификация вводит для случая «несколько Агентов за одним эндпоинтом A2A». `/.well-known/agent-card.json` отвечает, только когда публичный Агент **ровно один** (случай одиночного самостоятельного хостинга), иначе возвращает 404 и в тексте ошибки указывает на `agents.json` — назвать произвольно выбранную учётную запись «Агентом этого домена» было бы неправдой.
- **`streaming: false`**. Потоковые эндпоинты действительно есть, но в собственной форме Confer, а не в виде спецификационного `SendStreamingMessage`. Объявить возможность, которой стандартный клиент воспользоваться не сможет, хуже, чем не объявлять ничего.
- **`securitySchemes` не объявляются**. Спецификация предлагает там ключ API, HTTP-аутентификацию, OAuth2, OIDC или mTLS, а этот эндпоинт не принимает ни одного из них: ему нужен подписанный запрос. Вписать что-нибудь наугад — значит сказать клиенту, что он может аутентифицироваться способом, который наверняка отвергнут. Настоящее требование объявлено как **обязательное расширение** (`capabilities.extensions`, где `uri` — адрес RFC 9421, а `required: true`), и это ровно тот механизм, который спецификация для этого и предусмотрела.
- Карточка — это **документ обнаружения**, и её видимость в точности совпадает с видимостью `/.well-known/agents.json`: непубличный или отключённый Агент всегда отдаёт 404, иначе этот маршрут превратился бы в способ перечислить учётные записи, которые хозяин публиковать не собирался.

- **Объявляется только одна привязка.** Собственный диалект Confer живёт по тому же URL, но в карточку не попадает: §5.1 требует, чтобы все объявленные Агентом привязки были функционально равнозначны, а у диалекта нет жизненного цикла задач. Он обнаруживается через `/.well-known/agents.json`, и карточка не обещает ничего, чего не может выполнить.

### Слой сообщений (семантика Task)

`POST /a2a/v1/message:send` принимает спецификационный `SendMessageRequest` и возвращает `Task`. **Задача — это и есть один входящий вопрос**: её `id` — идентификатор того сообщения, `contextId` — разговор, в котором оно хранится, а состояние выводится из происходящего дальше; отдельной таблицы `tasks`, дублирующей тот же факт, не заводится.

Асинхронная модель Confer с её воротами согласия ложится прямо на автомат состояний из спецификации:

| Ситуация | Состояние |
|---|---|
| Агент отвечает | `TASK_STATE_WORKING` |
| Ответил | `TASK_STATE_COMPLETED` |
| Этот ход вообще не может начаться (модель не настроена или поставщик вернул ошибку) | `TASK_STATE_FAILED` |
| Отложено политикой `ask_user`, ждём хозяина | `TASK_STATE_AUTH_REQUIRED` (состояние прерывания, не конечное) |
| Хозяин отказал | `TASK_STATE_REJECTED` |

В двух случаях возвращать **нечего**, потому что строка вовсе не создавалась: незнакомый пир (откладывается как запрос на соединение) и прямой отказ по политике. Оба отвечают `403 PERMISSION_DENIED` и различаются через `ErrorInfo.metadata.confer_status` — выдумать идентификатор задачи, который на следующем вызове даст 404, было бы хуже.

Остальное поведение выверено по спецификации пункт за пунктом: тело ошибки имеет форму `google.rpc.Status` и **всегда** содержит `ErrorInfo.reason` (несколько ошибок A2A делят один HTTP-код, и `reason` — единственное поле, которое их различает); клиенту, не объявившему обязательное расширение, отвечают `ExtensionSupportRequiredError` по §3.3.4, а не ничего не объясняющим 401; `historyLength=0` означает **опустить поле целиком**, а не прислать пустой массив; `nextPageToken` присутствует всегда и равен пустой строке, когда следующей страницы нет.

Два намеренных отступления, оба записаны в комментариях к коду: ожидание блокирующего `message:send` **ограничено сверху** (55 с, после чего возвращается задача всё ещё в состоянии `WORKING`, чтобы клиент опрашивал) — §3.2.2 не предусматривает выхода по времени, а у вызова LLM верхней границы нет; идемпотентность по `messageId` (это MAY из §3.3.1) **не сделана**, потому что безопасный между арендаторами уникальный ключ требует области владельца, а формат передачи первого сообщения её не несёт.

## API консультаций (исходящий A2A по инициативе пользователя)

Позволяет пользователю (или действующему от его имени MCP-серверу) по собственной инициативе задать вопрос чужому Агенту, **который уже является контактом**, и затем забрать асинхронный ответ. Подпись и доставка целиком выполняются внутри шлюза; закрытый ключ его не покидает.

> Отличие от «API разговоров»: `/api/v1/conversations` + `/api/v1/stream` — это беседа с **собственным локальным LLM-помощником**; `/api/v1/consult` — это то, что уходит по A2A **к чужому Агенту**.

### POST `/api/v1/consult/:peerId`

Начинает или продолжает разговор с `type='consult'` (для каждого пира он один и тот же), подписывает и доставляет `message.type='question'`.

```jsonc
// тело запроса (consultRequestSchema)
{ "question": "Как ротировать ключи?", "code_context": "…необязательный код…", "language": "ru" }
```

| Ответ | Смысл |
|------|------|
| `201 { conversation_id, message_id, status: "sent" }` | подписано и доставлено |
| `502 { ..., status: "failed", error }` | доставка не удалась (пир не в сети, нет эндпоинта или проблема с подписью) |
| `403 not_a_contact` | пир не является контактом текущего пользователя |

### GET `/api/v1/consult/:conversationId/reply?after=:messageId&wait=:seconds`

Длинным опросом ждёт асинхронный ответ пира (он приходит на входящий `/a2a/v1/messages` со своим `thread_id`, и шлюз подвешивает его обратно в нужную ветку). Предел `wait` — 55 с.

- `200 { status: "answered", message }` — ответ получен
- `200 { status: "pending" }` — время вышло, ответа нет; можно опросить позже

### GET `/api/v1/consult/:conversationId`

Возвращает всю историю этой ветки консультации (не более 200 сообщений).

> Контракт: входящий A2A запускает автоматический ответ локального агента только для `message.type==='question'`; `answer` и `notification` лишь сохраняются и рассылаются, чтобы ответ на консультацию не превратился в бесконечный обмен.
